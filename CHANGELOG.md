# Changelog

All notable changes to this project will be documented here.

Version numbers follow VR2Gather major.minor, with an independent patch number for
fixes and improvements within a VR2Gather release cycle. Versions are derived from
git tags (see `FILEVERSION` / `OLDEST_COMPATIBLE_VERSION` in `datastore.py` for the
combined.json format version scheme).

## [Unreleased]

- Development-only tools removed: the simulators, soak, clock replay and timing scripts in `tools/` (only `tools/tap_test.py`, for the hardware tap tests, remains), and in the Unity project the demo-scene builder and the `Tests~` harness. The Python test suites stay
- Documentation: results of the two-computer hardware runs of 2026-10-13 and 2026-10-14; a phone hotspot or a cable when both machines are on WiFi; starting `VRTrunserver` from a normal window; checking a restarted BITalino and port 5002 before `VRTrun`
- `VRTsensors-emotibit` never waits for an LSL clock correction: liblsl measures it in the background, so it is polled. A new stream is held, its samples buffered by LSL, until the correction answers (at most `correction_wait`, 2 s), and its `connected` event then follows. Retrying senders that did not answer took 0.5 s each on the reading thread: with nineteen of them, nothing was read or sent to Unity for 9.5 s at a time, and the opening pass cost up to 2 s per stream
- `VRTsensors-emotibit` keeps the samples of a stream still held for its clock correction when the capture ends or is interrupted: they are read before the inlet closes, after a `connected` event with `time_correction_valid: false`. Closing it unread threw them away, so a short capture, or a stream that came back near the end of a long one, lost them all
- `VRTsensors-validate --study` counts EmotiBit samples with no `connected` or `time_correction` event before them: with no correction state recorded at all, a capture passed as corrected
- `VRTrunserver` declares `SENSOR_SUPPORT = 2`, which the Unity build's `VRTrunserver.ps1` reads from the module the environment would import. The script checked only the command names and `VRTsensors.FORMAT`, so a sensorless server on `PYTHONPATH` beside a current VRTsensors was reported Ready
- `tools/tap_test.py` judges only what it is told to expect: `--signal` (repeat; the first is the reference) and `--taps`. Each expected signal must show exactly that many taps, paired in order one to one, and start and end groups are reported separately against `--drift-ms`. It passed with an axis that felt nothing (dropped before judging), with half the taps missing (five matches sufficed), and with defaults looser than the test plan's. Without expectations it only lists signals and exits 2. The self-test covers each of those cases
- `VRTsensors-emotibit` records whether LSL clock correction succeeded (`time_correction_valid` on `connected`) and asks a sender that did not answer again at every network search, recording the answer as a `time_correction` event; a failed correction was recorded as a plain `0.0`, indistinguishable from a real one, and kept for the inlet's life. `--study` counts the samples dated without a known correction
- `VRTsensors-emotibit --source DEVICE_ID` records only that EmotiBit's streams, and the header names it (`sources`); `--list` prints each stream's device ID. LSL shows every computer every outlet, so in a two-participant session each capture recorded both EmotiBits and ingest filed both under each participant. Ingest now refuses a participant's capture holding samples of two devices, and a device under two participants; `--study` reports an EmotiBit capture without `--source` and a capture holding two devices; an unbound capture that sees a second device warns
- `VRTsensors-validate --study` accepts only `dirty: false` with a nonempty `revision` as committed code: a checkout whose git status failed (`dirty: null`) passed as clean. The check covers `VRTsensors/src`, as documented
- `VRTsensors-bitalino` times batch arrivals on the performance counter and puts samples on the wall clock with one mapping per connection: a time synchronisation that stepped the wall clock mid-connection was read as delivery delay and counted as lost 16-sample cycles (48 samples for +0.5 s, 96 for +1 s), and later samples were shifted as if lost. `clock` records carry the mapping (`epoch`); the step is still reported as `clock stepped`
- `VRTsensors-bitalino` that gives up on a board that never answers ends with `stopped` (`reason: unreachable`) and exits 1, where it ended `finished` with exit 0, so a launcher and the operator can tell it from a capture that ran
- Documentation: getting and building the Unity project (Git LFS, Unity 6000.3.10f1, cwipc, orchestrator reachability, a command-line build), clock synchronisation commands, EmotiBit stream names, conversion of BITalino values to physical units from PLUX's datasheets, what a session records about a person and how to handle it, and corrections where the pages had drifted from the code
- `VRTrunserver` refuses a run, before starting the player and with the reason in its response, when a capture's `--output` already holds a recording (two runs started in the same minute share VRTrun's working folder, and every capture then refused its output and exited while the player ran on) or when a capture exits within two seconds of starting (a bad argument, a malformed `participant.json`)
- `constraints.txt` pins every third-party package to the versions tested; the install instructions use it. A fresh install without it already resolved newer `pandas` and `pylsl` than the tested environment
- The `capture` record also names the git commit the code ran from and whether it had uncommitted changes (`revision`, `dirty`), since the installed `version` of an editable install goes stale after a pull; and the Python and dependency versions
- Participant and session identity: `participant.json` (`{"participant": "<pseudonym>"}`) in a role's configuration folder and an optional top-level `session.json` are copied into every capture header; ingest puts `participant` on every sensor record, maps roles to participants in its summary, and refuses a role whose captures name two participants. A malformed `participant.json` stops a capture before it starts
- `VRTsensors-validate --study` also requires format 2, a participant ID and a committed code revision, and the checker notes how far the wall clock moved against the monotonic clock over a capture
- Captures are asked to stop instead of being killed: `VRTrunserver` and the Unity editor hold each capture's stdin, set `VRTSENSORS_STOP_ON_STDIN_EOF=1`, close it to stop, and kill only what is still running five seconds later. A capture that stops this way, at Ctrl+C or at the end of `--duration` releases its device and writes a final `stopped` record, so a killed or crashed capture can be told from a complete one; `VRTsensors-validate` reports a format-2 capture without one
- Unity: a machine whose only accelerometer is an EmotiBit gets wind again (a negative resting level counted as "none yet" and was reset every frame; an EmotiBit also has its own full scale in g); a remote participant's lantern no longer stays tilted and off-size from being copied mid-pulse; `SensorShare` survives a scene without an orchestrator; the editor's hints give a BITalino command that records something; the board names both sources of skin response and shows digital lines as 0 or 1. Harness: 124 checks
- `VRTrunserver` and the Unity editor's launcher name every sensor that `sensors.json` starts and the `sensors.local.json` in use leaves out, with a warning. The local file still replaces the shared one, so that a machine can leave a sensor out, but a sensor dropped that way no longer vanishes silently: on the two-machine example, participant1's hand-written local file had quietly taken out its EmotiBit
- `VRTsensors-bitalino` dates each sample by its number since the connection opened, on a line fitted under the batch arrivals, instead of back-dating it from its batch's arrival: Bluetooth's per-batch delay (up to 175 ms on our recordings) no longer lands in the timestamps, and they always increase. In simulation 99% of timestamps are within 3.5 ms of the true sample time, against 140 ms before
- `VRTsensors-bitalino` finds whole lost cycles of 16 samples, which the 4-bit sequence number cannot show, by timing, and reports them as `gap` with `detected: timing`; sequence gaps say `detected: sequence`
- Every capture starts with a `capture` record (`format` 2, VRTsensors version, command line, host) and carries a `clock` record every ten seconds (wall and monotonic clock, plus each sensor's clock state). Both stay in the file and are not sent over `--udp`. Ingest records each capture's format and version in its summary and refuses a newer format
- `VRTsensors-validate` judges steps back in time by format (a note in format 1, a finding from 2), and reports losses found by timing, a wall clock stepped mid-capture, and a capture in a newer format
- `VRTsensors-emotibit` survives a sender that does not answer LSL's clock check: pylsl raises its own `TimeoutError`, not the built-in one, so the handler never ran and one slow stream ended the whole capture. The stream now records `time_correction: 0` with a warning, as intended
- `VRTsensors-emotibit` no longer records a restarted stream twice. Inlets were opened with liblsl recovery, which silently re-attached the old inlet to the restarted outlet while the next resolve opened it again under its new uid; in a simulated Oscilloscope restart 220 of 870 samples were duplicates. A lost stream is now closed and recorded as `disconnected`, the network is searched every second until it returns, and its successor is opened once
- `VRTsensors-validate` reports a signal recorded twice: two streams of one device and signal whose samples overlap by more than half a second
- Empatica E4 support removed: `VRTsensors-empatica`, its tests, its `bleak` dependency and every mention in the documentation and examples. The E4 was in the original plan, but the only wristband available had a broken battery and Empatica has discontinued the device, so it was never run on hardware. The Sleeping Giant's pulse and snow now come from the EmotiBit
- `VRTsensors-bitalino --setup` writes the `--address` it just connected through, instead of keeping the one already in the file: run against the example configuration, it used to leave the example's `COM5` in place, so the capture it wrote pointed at a port that belonged to another machine
- Documentation reorganised into one numbered set of pages in `docs/`, in reading order and in three parts (using it, building on it, reviewing it), with one home per topic and each figure used once; the command reference moved from `VRTsensors/readme.md` into `docs/10-command-reference.md`
- Documentation rewritten for researchers who are not software specialists: step-by-step install and run instructions for Windows, one voice throughout, and a redrawn, consistent set of figures
- `VRTrunserver` no longer imports the `VRTsensors` package, which its own requirements never declared: a machine that installed the server alone failed at startup. It honours `sensors.local.json` and `sensors.json` with its own five-line lookup, checked against the package's by a regression test
- The three capture commands share one output path: a mistyped `--udp` no longer leaves an empty capture file behind, a UDP send error goes to stderr instead of into a capture written to stdout, and captures and `--setup` read and write UTF-8 explicitly
- A `sensors.local.json` beside a role's `sensors.json` wins over it and is gitignored: a machine says what is plugged into it without editing the shared example, `--setup` writes the local file when there is an example to preserve, and both the runner and the editor print which of the two they used
- `VRTsensors-bitalino --duration` counts acquisition, not wall clock: neither the seconds spent opening the device over Bluetooth nor a failed attempt and its retry wait are taken out of the capture, so `--duration 30` records thirty seconds of samples. Because it can no longer expire while nothing is connected, `--connect-timeout` (default 60s) is what ends a capture from a device that never answers
- `VRTsensors-validate` counts an acquisition `unreachable` event as a finding: a capture that gave up on a device that never answered is short by decision, and the verdict says so
- A BITalino transport is released even when `stop()` fails, which is the usual way a dropout presents, so a reconnection no longer finds the serial port still held
- Muscle and brain activity is computed per sample where the samples arrive, not once per frame from whichever sample was last, so a burst that begins and ends inside one frame is no longer lost; the envelope travels in the shared snapshot, so a remote participant sees what the machine that measured it sees rather than recomputing one from two values a second
- The Unity listener's UDP socket is marked not to be inherited by child processes: a capture started with redirected output inherited the handle and held the port for as long as it lived, so the next Play failed with `Cannot listen on UDP 9010` while nothing visible was listening
- A configured sensor channel that stops arriving no longer counts as bound: the scene keeps its name so a sign can say what was lost, falls back to a live device when there is one, and never shows an unplugged electrode as a calm mind
- Capture validation checks record shape and acquisition faults, separates device streams and channel ranges, resets sequence state on reconnect, and keeps exit status independent of verbosity
- Sensor runner accepts UTF-8 BOM configs written by Windows PowerShell; analysis examples and timing claims corrected, with consistent, regenerated documentation figures
- The Unity sensor board shows a device whose streams are advertised but silent (an EmotiBit whose Oscilloscope relays nothing) as waiting, with the hint to check the device, instead of not listing it at all: a stream's channel now exists from its `connected` event
- BITalino setup skips sequence-gap events when collecting port readings, so a lost sample no longer aborts setup
- `VRTsensors-bitalino` takes the button on a digital input (`--channel I1=btn`) and refuses it on an analog port: released, an analog button floats and reads a few percent of the port before it (0.030 x A1 - 1.65, R2 0.96 over 245k samples on the development board), so its "presses" were the accelerometer's swings. A press is the line low for 20 ms, dated from its first low sample
- `VRTsensors-bitalino` acquires named ports only, and no longer guesses what a port is from its signal: the `module` event carries the name given, `inferred: false`, and unnamed ports are not captured (an empty port behind a busy one records its neighbour's shadow). The `connected` event states each port's resolution, since a fifth and sixth acquired port come as 6-bit. `--setup CONFIGDIR` shows what every port reads and asks about all eight
- `VRTrunserver --executable` works outside a build tree: without a `VR2Gather.exe` above it, the server no longer refuses to start before reading its arguments
- The Sleeping Giant gains five signals with a sign each: the EmotiBit pulse lights a heart-stone in its chest and cool skin makes it snow; a BITalino light sensor brings night (and easier sleep), a muscle sensor clenches its fists, a brain sensor gives it dreams. A named port drives only its own effect, and movement no longer wakes the giant
- `examples/amplify-demo` holds ready-made settings for the giant with sensors, on `SimpleAvatar`: two machines (`config/`), one machine with both sensors (`config/self/`), and one machine that creates the session by itself and leaves after 120 s (`config-single/`)
- The Unity side no longer classifies channels or detects presses; it displays the acquisition's `module` and `press` events, and shares each participant's channel table with the other participants over VR2Gather's session events so a scene can show whose signal is whose
- Sensor runner reaps captures and launcher children after failures, normal exit and kill without Unity; Windows paths and regression checks included
- Sensor ingest reports empty captures and interrupted final records while preserving valid samples; rejects nonfinite timestamps
- New `VRTsensors` package for physiological sensor acquisition, with `VRTsensors-bitalino`: captures one BITalino device to JSON lines, one record per sample, with per-sample timestamps, sequence-gap detection and automatic reconnection after a dropout. Field names are provisional until the measurement contract defines them
- `test_bitalino.py` exercises record shape, lost-sample detection and the reconnect path against a simulated device
- `VRTsensors-emotibit`: captures EmotiBit signals relayed over LSL by EmotiBit Oscilloscope, one record per sample per stream (EmotiBit is multi-rate: EDA 15Hz, PPG and IMU 25Hz, temperature 7.5Hz), with wall-clock-corrected timestamps, loss and stale detection, and `--list` to discover the stream names configured in the Oscilloscope's patchcords
- `VRTsensors-emotibit --scan` listens on the EmotiBit advertising port to tell "the device never joined the network" apart from "the device is here but the Oscilloscope cannot see it", distinguishing remote devices from this machine's own discovery broadcasts
- EmotiBit records preserve LSL source identity so same-named streams from multiple participants do not overwrite each other, and captures with no samples now fail
- `VRTsensors.ingest` registers a `sensors` annotation step, so captures merge into a session's `combined.json`: `VRTstatistics-ingest --module VRTsensors.ingest -a sensors`. Captures are discovered at `<workdir>/<role>/*.jsonl` beside the per-role logs, and put on session time using the clock offset `SessionNormalizer` already measured for that role, rather than a second alignment scheme
- `VRTsensors-bitalino` and `VRTsensors-emotibit` gain `--udp HOST:PORT`, sending every record as a UDP datagram alongside the capture file, for a realtime consumer such as Unity. Fire-and-forget by design: a consumer that is absent or slow must not affect the capture, which remains the record. Note that `--batch` sets the latency floor — at 100Hz a batch of ten delivers in 100ms bursts
- `VRTsensors-bitalino` and `VRTsensors-emotibit --output` create the output directory if it does not exist, so a capture aimed at a fresh session folder does not fail before connecting
- `VRTrunserver` starts the sensor captures listed in the role's `sensors.json` alongside VR2Gather and stops them when it exits, so their `.jsonl` files come back with the other results and the `sensors` annotation merges them; see `examples/amplify-demo/config/self/sensors.json`
- Both sensor commands refuse to overwrite an existing non-empty `--output` file: a capture is a record
- `test_sensor_ingest.py` covers the merge, the direction of the per-role clock correction, and the refusals
- `test_emotibit.py` exercises the real LSL path — resolution, inlets, clock correction, loss and stale detection — against streams published in-process, so it needs no hardware

## [1.4.1] — 2026-07-07

- `VRTstatistics-ingest` gains `--module MODULE` (previously only on `VRTstatistics-annotate`), so ingest-time annotation steps defined outside VRTstatistics can register themselves in one step: `VRTstatistics-ingest -a <name> --module <module>`
- `--module` (both `ingest` and `annotate`) now falls back to searching upward from the current directory for a matching `<module>.py`/`<module>/` package when a plain import fails — lets a per-experiment analysis module (e.g. `vrts_trolley.py`) live at an experiment repo's root and still be importable from a session subdirectory several levels below, with no packaging/install step
- New internal `scripts/_modimport.py` shared by `ingest.py` and `annotate.py`
- readme: document the emerging per-experiment `vrts_<experiment>.py` pattern (custom `View`s + `AnnotationStep`s + `--module`); flag `VRTstatistics-plot`'s `--import` as inconsistent with the other two and due for unification later
